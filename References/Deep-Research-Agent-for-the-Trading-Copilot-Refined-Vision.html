1. Thesis: What We're Building

We are building a trading copilot — not a screen-scraping dashboard, not a coding tool, not a generic chat agent. It is a proactive, learning, multi-agent system that lives alongside the trader to:

  • Observe positions, market data, and user behavior in near real-time
  • Analyze via multi-step deep research (data + LLM reasoning)
  • Learn by reflecting on past trades and updating its own memory and rule set
  • Act by proposing rule changes, surfacing alerts, and generating structured research reports

The app's core intelligence comes from assembling well-maintained open-source agent modules, not from building a monolithic AI from scratch.

2. What This Is NOT

Misconception Reality
A coding assistant agent (OpenCode) Not relevant. We aren't writing code inside the app.
A generic chatbot The agent has memory, tool use, and proactive behavior — it initiates, not just responds.
A fully autonomous trading bot The agent proposes, explains, and recommends. The human decides and executes.
A monolithic AI We compose 5+ OSS modules together (Mem0, LangGraph, BabyAGI pattern, etc.)

3.1 Component Breakdown

A. Mem0 — Persistent Memory Layer

  • What it is: Open-source memory layer with vector search (MIT)
  • Role in copilot: Stores user preferences (risk tolerance, trading style), trade patterns, recurring mistakes, research context
  • How it's called: HTTP from Rust backend; also callable from Python microservice
  • Key data stored:
  • User facts ("I prefer 2% max risk per trade")
  • Trade reflections ("I exited TSLA too early because of FOMO on 6/10")
  • Research summaries that the deep research agent has produced
  • Rule proposals the user has accepted/rejected

B. LangGraph — Deep Research Agent

  • What it is: LangChain's graph-based agent orchestration framework
  • Role in copilot: Executes multi-step market analysis — fetches data, runs interim analysis, produces structured markdown reports
  • Research workflow: 1. User asks "analyze NVDA after earnings" or agent proactively checks portfolio 2. LangGraph agent spawns sub-tasks: fetch price data → check news sentiment → analyze technical indicators → consolidate into report 3. Report is streamed to dashboard and saved to memory
  • Key design: Each research run is a directed graph. The agent has tools: fetch_prices, search_news, get_positions, read_memory

C. BabyAGI Reflection Pattern — Learning from Past Trades

  • What it is: The reflection loop from BabyAGI (Execute → Evaluate → Reflect → Update Memory)
  • Role in copilot: Runs as a periodic background task (e.g., every night after market close, or on demand)
  • Reflection workflow: 1. Gathers today's trades from the Rust backend 2. Analyzes each trade: entry rationale, exit timing, P&L, market conditions 3. Generates a "lesson" and stores it in Mem0 4. If a pattern repeats (e.g., "3rd time exiting on a red candle within 30 min"), proposes a new rule to the user
  • Output: reflection_report_{date}.md stored in memory, and optionally a rule proposal

D. Rule Engine (json-rules-engine)

  • What it is: A JSON-based rules engine (JavaScript or ported to Rust)
  • Role in copilot: Executes user-defined or agent-proposed conditional trading rules
  • Example rules:
  • "If NVDA drops 5% in one day AND I hold it → notify me with options strategy analysis"
  • "If my day P&L exceeds -3% → disable new trades and summarize why"
  • "If the VIX is above 30 → tighten all stop losses to 2%"
  • Memory integration: The reflection loop can propose rules. User accepts/rejects them. Accepted rules go into the engine.

4. Data Flow: End-to-End Scenario

Let's trace a realistic scenario from start to finish.

Scenario: User holds AAPL, agent notices unusual options activity

  1. Rust Backend polls positions every 15s. AAPL position is detected.
  2. Research Agent (LangGraph) is triggered — either by a user question ("what's up with AAPL?") or by a weekly scheduled check.
  3. LangGraph executes a graph: - fetch_price_data(AAPL, 5d) → price up 2%, volume rising - search_news("AAPL unusual options activity") → 3 results about large call buying - fetch_options_chain(AAPL) → elevated put/call ratio - read_memory("last AAPL analysis") → previous analysis from 2 weeks ago
  4. LangGraph consolidates into a structured report: - Title: "AAPL Unusual Options Activity — June 13, 2026" - Sections: Summary, Price Action, News Sentiment, Options Flow, Recommendation
  5. Report is streamed to the dashboard via SSE (token by token, for live feel).
  6. Report is saved to Mem0 as a research memory.
  7. Reflection Loop (BabyAGI pattern) runs overnight. It sees today's trades, including how the user acted on the AAPL report. - If the user followed the recommendation and profited → stores "AAPL options flow analysis was valuable" in memory - If the user ignored it and lost → stores "Consider setting AAPL alert rules"
  8. Rule Engine gets a proposed rule: "If unusual options activity detected on a top-3 position → auto-generate analysis report".

7. Proactive Agent Behaviors (The Copilot Feeling)

The agent shouldn't just sit there waiting. It operates on a heartbeat:

Trigger Agent Action
New position opened Generate initial analysis report for that symbol
Position P&L crosses -5% Run deep research on the symbol, check news, propose action
End of trading day Run reflection loop, produce daily summary
Weekly on Sunday Generate "Week Ahead" report for top 3 positions
Token expires in 24h Push notification and show "Re-auth" button timer
Same mistake pattern repeats Propose a rule to prevent it
Market volatility spike Suggest portfolio hedge strategies based on current positions

These behaviors are expressed as scheduled graph runs in LangGraph, each with a trigger condition checked by the Rust backend.

9. Open Questions / Next Decisions

  1. Reflection schedule — End of day? End of week? After every trade? Need to test user tolerance for frequency.
  2. Rule proposal UX — Should rules auto-enable with a grace period, or require explicit confirmation? Leaning toward explicit confirmation.
  3. Local vs. cloud LLM — Ollama local for low latency + privacy. API models (GPT-4o, Claude Sonnet) for heavy research. User selects per task.
  4. Multi-broker priority — Schwab first (7-day OAuth constraint). Then Alpaca (API key only, easier). Then IBKR.
  5. Report verbosity — Some users want one paragraph. Some want a multi-page research report. Let users set depth preference (stored in Mem0).
