# OPRA websocket probe results — 2026-07-09 (P-1 / P-3)

Live market-hours run (~13:40 ET), `scripts/opra_ws_probe.py`, read-only.
Closes the design doc's Phase-3 probe gates (§8 P-1, P-3).

## P-1 — websocket mechanics (all confirmed)

- **Connect + auth**: `wss://stream.data.alpaca.markets/v1beta1/opra`, msgpack-only.
  Hello `{"T":"success","msg":"connected"}` → send `{"action":"auth","key","secret"}` →
  `{"T":"success","msg":"authenticated"}`.
- **Message schemas** (exactly as design §data-sources table):
  - trade: `{T:"t", S:<occ>, t:<msgpack Timestamp→datetime>, p, s, x:<exch char>, c:<ONE condition char>}`
    — note `c` is a single string, NOT a list like equities SIP.
  - quote: `{T:"q", S, t, bx, bp, bs, ax, ap, as, c}`.
- **Subscription cap**: bulk-subscribed **1,506 contract trade feeds → ACKed, no error**.
  The assumed 1,000 hard cap did not trigger; treat 1,000 as our own budget, not a vendor wall.
- **Connection limit: ONE ws connection per account.** A second concurrent connection
  auths to `{"T":"error","code":406,"msg":"connection limit exceeded"}`; the FIRST
  connection survives (new one refused, no takeover). Implications:
  - prod stream client must be a process singleton;
  - dev probing while prod streams will be refused — stop the prod stream first;
  - the equities SIP stream (separate URL) does NOT contend — both ran concurrently fine.

## P-3 — latency + condition codes

- **Trade lag** (receive − print ts, 823 prints/60s): **p50 = 12 ms, p90 = 14 ms, max = 117 ms.**
  vs the 30s REST poll: streaming is effectively at-tape.
- **Condition-code frequencies** (60s, 9 active near-dated contracts):
  `I` (odd lot) 507 · `a` (auto execution) 259 · `j` 22 · `g` 18 · `S` (ISO sweep) 12 · `f` 5.
  `S` prints are present and frequent enough to corroborate SWP-1 clustering as designed.
  No condition seen that invalidates F-1/F-2 assumptions.
- **Quote volume is the flood risk**: 9 contracts produced **~275 quote msgs/s** vs ~14 trade msgs/s
  (20:1). Extrapolating, full-set quote subscription (hundreds of contracts) is untenable.

## Consequences for the Phase-3 build

1. **Trades broad, quotes narrow.** Subscribe trades for the whole managed set (≤1,000 budget);
   subscribe quotes ONLY for a dynamic "hot" subset (contracts with a recent print), LRU-capped.
   DIR-1 uses the cached stream quote when fresh, else falls back to `polled_quote`/`none` basis.
2. **Stream is additive; the 30s poll stays running as the permanent baseline** (multi-user
   fallback decision 2026-07-09). Event ids are deterministic (`..._blk_{ts_ms}`, per-day
   UV/pressure ids) and the DB upserts on id — both paths running concurrently dedupe for free.
3. **Singleton + fail-soft**: one stream task, reconnect with backoff, and on persistent failure
   the poll loop alone keeps the feature alive (no alerting gap, just back to 30s granularity).
