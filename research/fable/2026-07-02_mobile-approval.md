# Phone-Approval Flow Audit — help_me_trade
*Fable 5 audit · read-only · 2026-07-02 · proposal → APNs/Live Activity → Face ID → approve → chokepoint → confirmation.*

**Verdict up front:** the approve→execute *core* is genuinely well-built (atomic, honest, fail-closed), but the flow is **not yet "step-away trustworthy":** delivery is fire-and-forget with no fallback or missed-proposal accounting, the Live Activity contract is half-implemented, there is no fill-report loop, and the biometric gate — real as fat-finger protection — is **not an authorization factor the server can verify.**

**Secrets check:** `secrets/apns.p8` is **NOT committed** (`git ls-files secrets/` empty; `.gitignore:42`; file `0600`). No APNs-key exposure.

## 1. End-to-end flow map
1. **Create** — all sources converge on `propose_trade()` (`trading/proposal_intake.py:113`): kill-switch + market-hours + account gates, sizing vs buying power, a **pre-check `RiskEngine.validate()`** (so junk never reaches the phone), then `create_phone_proposal()` (`trading/proposals.py:310`) writes `pending_phone` with `payload_hash` = SHA-256 of canonical intent + `expires_at`. **Airtight.**
2. **Push** — `send_proposal_push()` (`signals/push.py:287`) signs an ES256 APNs JWT to every active token, carrying `proposal_id`+`payload_hash`+`expires_at`. **NEVER raises, all failures swallowed** — weakest hop (R1). Parallel `start_proposal_live_activity()`.
3. **Render** — lock screen: actionable `TRADE_PROPOSAL` with Approve (`isAuthenticationRequired:true`, `notifications.ts:58`) + Reject. Foreground banner deliberately suppressed (iOS doesn't enforce auth on foreground taps — a **correct subtle safety choice**); in-app Inbox polls pending every 10s.
4. **Biometric + approve** — (a) lock-screen action → Face ID → `handleApprove()` POSTs approve w/ push hash; (b) in-app card → `authenticateForApprove()` (`proposal-card.tsx:66`, fail-closed) → same POST.
5. **Server approve** — `POST /api/proposals/{id}/approve` hard-requires `payload_hash` → `approve_proposal()`: expiry fail-safe, hash check, then the **atomic claim** (`db/paper_orders.py:308`, `UPDATE ... WHERE status='pending_phone' AND expires_at>now`) — double-tap/second-device/expiry races collapse to one winner. Tested.
6. **Execute** — `submit()` with `client_order_id=execution_id` (broker-idempotent), RiskEngine again, kill-switch first; persist failure never masks a placed order. **Airtight.**
7. **Confirm** — HTTP response → honest card banner; Live Activity UPDATE/END → **broken (R2)**; fill confirmation → **doesn't exist (H3)**.

## 2. Is the biometric gate real or cosmetic?
**Real as anti-fat-finger, cosmetic as authentication.** Both gates run *before the client sends the request* — the server sees nothing of them. The approve endpoint checks only the `SecurityMiddleware` static token + the `payload_hash`, and the hash is **not a human-held secret** — `GET /api/proposals/pending` returns it to any token-holder. So **anyone with the single unscoped optional `API_TOKEN` can list + approve (or create-and-approve) orders from `curl`, zero biometric.** No per-device identity, no rate limiting, `decided_by` always `"phone"`, token accepted via query param + in the WS URL → lands in access logs. Acceptable *today* only because: tailnet-only, host-allowlist, paper-fenced. Crux: **the server cannot distinguish "Matt's face" from "Matt's token."**

## 3. Ranked findings
### CRITICAL
**S1 — A single static token is the entire authorization for money movement; biometrics are unverifiable.** (`auth.py:10,59-67`; `ai_routes.py:134,214`) Token leaks via access log / backup / any tailnet process → attacker lists pending, approves, or creates-and-approves. No rate limit, no 2nd factor, no scoping (watchlist token = trade-approval token), no approver-identity audit. Blast today: paper + RiskEngine caps. At live: the brokerage account. **#1 gate before real money.**

### HIGH
**R1 — Delivery is at-most-once, unaudited, no fallback.** `send_proposal_push()` swallows every failure; no retry/re-push before expiry, no delivered record (`delivery` is constant `"phone"`), no secondary channel, no alarm when 0 devices reached. APNs `410 Unregistered` logged but **not deactivated** (`push.py:176`) → stale tokens degrade silently after reinstall. `apns_use_sandbox` **defaults to sandbox** (`settings.py:916`) — one env slip = prod build receives nothing, silently. Biggest "can he step away?" breaker.
**R2 — Live Activities can never be updated/ended: the server half was never built.** The app POSTs `{activity_update_token, device_token}` **without** `proposal_id` (`use-live-activity.ts:62`), the route 400s (`device_routes.py:70`), error swallowed → `list_update_tokens(proposal_id)` always `[]` → `end_proposal_live_activity` no-ops. The repo's own ACK doc says exactly this (`SERV_REPLY_live_activity_ACK.md:65-71`). Lock-screen cards stay "Pending approval" **with live Approve/Reject buttons** until stale-date, even post-execution. Money-safe, maximally trust-corrosive.
**R3 — Expired-unanswered proposals vanish without a trace.** `→ expired` only happens inside `approve_proposal` (i.e. only if someone tries late). If nobody acts: row sits `pending_phone` forever, no "you missed BUY 40 NVDA" push, no decision-journal `expired` entry (learning loses the misses), pending list just stops returning it. "Quiet inbox" == "missed three setups."
**H1 — The client lies on response loss: "Network error — the trade was not sent."** (`proposal-card.tsx:141`) If the connection drops *after* `submit()` succeeded, it WAS sent. Retry → `already_decided` rendered as "already decided"; server returns `current:"executed"` but the client drops it. Correct copy: "Result unknown — checking…" + `GET /proposals/{id}` reconcile. One "it said not sent but bought $8k AAPL" ends trust permanently.
**H2 — Crash window orphans `approving` proposals; no reconciler.** Between claim and terminal transition, a crash strands the row: nothing sweeps `approving` on startup, phone saw a network error, pending list hides it. Needs a startup/periodic reconciler (`approving` older than N min → look up execution by `proposal_id` → resolve + notify).
**H3 — "Executed" means *submitted*; nobody reports the fill.** Chokepoint execution notification is cockpit-only (`push=False`); no fill/partial/day-order-expired/limit-never-filled push. Only `auto_execute_entry` pushes — the *unattended* path reports better than the *attended* one. The reporting half of the approved-trade loop is missing.

### MEDIUM
**M1 — Card renders on incomplete data.** `list_pending_proposals` omits `limit_price`/`account_id`/`created_at` that the card renders → a **limit proposal's sizing strip reads "Market"**, account never shown, inbox sorts `ts=0`. Hash binds true terms, but the human approved terms he couldn't fully see. **M2 — Lock-screen approve under iOS suspension + cold-start replay** can silently send nothing, or re-fire a handled APPROVE → 409 → "Not executed" *after* a success (money-safe, trust-noise; persist handled IDs). **M3 — Approval needs the tailnet; the push doesn't** — notification at soccer practice, VPN asleep → approve fails; at least say "check your VPN"; ideally Tailscale on-demand/relay. **M4 — Device registration is identity-free** — any token-holder registers any token + receives every proposal incl. `payload_hash`.

### LOW
**L1** `/docs`+`/openapi.json` unauthenticated (schema disclosure to tailnet peers). **L2** Live-Activity Reject = one unauth lock-screen tap, errors swallowed (pocket-press discards a good setup, no feedback). **L3** token via query param + WS URL → access-log leakage; prefer header-only. **L4** dormant Expo legacy push complexity.

## 4. Does it deliver the north-star?
**The tap itself: yes** — Face ID on the lock screen, honest verdicts (incl. "Blocked by the risk engine"), a card that never paints failure as success, and the strongest server spine in the codebase (atomic claim, idempotent submit, risk-gated, honest expiry).
**The step-away promise: not yet.** Trust-while-away needs three guarantees this lacks: (1) *"if the agent found something, I heard about it"* — broken by R1 + R3; (2) *"what I see is current"* — broken by R2 + M1; (3) *"after I approve, I know what happened"* — broken by H3 + H1 + H2 + M2. Today he can step away and *approve*; he cannot step away and *stop checking*. The gap is the reliability shell, not the execution plumbing.

## 5. What must be true before real money (prioritized)
1. **Bind approval to the device, not a shared string (S1).** Per-device Secure-Enclave keypair (`kSecAccessControlBiometryCurrentSet`) signs `proposal_id+payload_hash+nonce`; server verifies the signature → Face ID becomes server-verifiable + per-device revocable. Interim even for paper: separate approve-scope token, header-only, rate-limit + lockout, log approver identity.
2. **Delivery you can prove (R1, R3).** Persist per-proposal APNs results per device; retry w/ backoff inside TTL; deactivate 410 tokens; a fallback channel when zero ACK; an expiry sweeper that journals + pushes a "missed: …" digest. Silence must mean "nothing happened."
3. **Close the confirmation loop (H3, H1, H2).** Order-status tracking → push filled/partial/canceled/unfilled-at-close; replace "not sent" with "result unknown" + reconcile; surface `current` on `already_decided`; startup reconciler for stuck `approving`.
4. **Fix the Live Activity contract (R2).** Implement the documented `proposal_id` correlation (or resolve it client-side before registering); test the no-`proposal_id` path.
5. **Show the whole truth on the card (M1).** Return `limit_price`/`order_type`/`account_id`/`created_at`; for real money add est. notional + account **money type** (real vs paper) — he must see which pocket the trade leaves.
6. **Un-break the away transport (M3)** — VPN-aware error copy → then the typed live double-gate + per-account/live caps already in the plan.

**Bottom line:** the hard, dangerous 20% — the atomic, risk-gated, idempotent approve→execute spine — is built and tested. What's missing is the unglamorous reliability shell: guaranteed delivery, guaranteed reporting, and a server-verifiable identity for the man doing the tapping. Those three are the difference between a *demo* of the life-changing unlock and the unlock itself.
